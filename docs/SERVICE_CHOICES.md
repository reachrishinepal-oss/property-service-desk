# Service choices

Why each Azure service in this product was chosen over its nearest alternative. One to three rows are added per build session.

| Session | Scenario | Chosen | Rejected alternative | When the alternative wins | Exam trap | Exam skill | What a client would ask |
|---|---|---|---|---|---|---|---|
| S00 | Residents chat with the service desk during the day. Traffic is low, spiky and live, so answers must come in seconds with no commitment. | Global Standard (pay per token) | Global Batch, Global Provisioned, Data Zone Standard | Batch wins for bulk work that can wait up to 24 hours at about half the price, such as scoring a whole month of tickets. Provisioned wins when throughput and latency must be reserved, for example a call centre with steady heavy load, accepting that reserved capacity is billed whether used or not. Data Zone wins when a client's rules say processing must stay inside a defined data zone (check which zones suit Dubai clients in S01, ADR-001). | Batch is cheaper but is wrong for live chat. Provisioned guarantees capacity, not a quoted uptime figure. | 1.2.b, 1.2.c | If our volume doubles, what do we pay, and where is our data processed? |
| S00 | The app signs in to the Foundry project from a laptop today and from a deployed service later. | Keyless sign-in with Microsoft Entra ID (`DefaultAzureCredential`) and the Foundry User role | API key | A key wins only when the caller cannot use Entra, such as an older tool or a third-party service that accepts only a key, or for a short throwaway test. Frequent or independent calls are not a reason, because the SDK refreshes tokens by itself. | Key-based calls bypass role-based access control. Owner and Contributor do not include Foundry data permissions, so the Foundry User role is still needed. | 1.3.d | Who called the model, and can you cut off one person's access without changing anything for others? |
| S01 | Triage of resident requests in live chat, judged on a 20-request set with an answer key. | gpt-4.1-mini (`ai103model1`) as the default, with gpt-5 (`ai103model3`) as the documented upgrade | gpt-5 as the default; gpt-5-mini | gpt-5 wins when a client weights accuracy over cost and speed: 18 of 20 right against 15, but about 2.5 times slower and about 20 times the output tokens. gpt-5-mini lost the rule agreed before the run (14 of 20, slower, more tokens). | The quality index and leaderboard are general benchmarks, not your task; reasoning models spend hidden reasoning tokens; a model marked Deprecated still has a retirement date (2027-04-14 for gpt-4.1-mini). | 1.1.a, 2.1.d | "Why not just use the best model?" |
| S01 | Where a Dubai client's resident data is processed and stored. | Global Standard in East US 2 | Data Zone Standard; a deployment in a UAE region | Data Zone wins when a client requires processing inside a named zone (US, EU or Asia Pacific; there is no Middle East zone on the page read on 15 Oct 2026). A UAE region wins when a client requires data to stay in the UAE, once model availability there is confirmed (not confirmed yet). | The deployment type decides where prompts are processed; the resource's region decides where data sits at rest. Global Standard may process in any Azure region. | 1.2.b, 1.2.a | "Where is our residents' data processed and stored?" |
| S02 | A resident chats over several turns and the history contains personal details such as a unit number and family circumstances. | Manual chaining: the app keeps the message list and resends all of it every turn | `previous_response_id`, where the service holds the history | `previous_response_id` wins when the history does not need to be edited or redacted and the team wants less to build: the app sends only the new message and an id, and in production there is no conversation database to run. The history is stored in the client's own Foundry resource, in the same geography, for 30 days by default according to a Microsoft Q&A answer read on 17 Nov 2026. | Either way the model reads the whole history on every call and the input tokens still grow (31 to 131 in a two-turn test with `previous_response_id`); the `instructions` of an earlier call are not carried over, so the rules must be sent again. | 2.1.a, 2.1.e | "Where is the conversation stored, and can personal data be removed from it?" |
| S02 | The assistant needs standing rules (triage job, no promised actions, emergency steps) on every call. | The `instructions` parameter, sent on every call and kept apart from the message list | The rules as the first item of the message list; the rules inside the first resident message | The first item of the list wins when the app chains with `previous_response_id` and wants the rules to travel with the stored history; that behaviour is reported by developers in OpenAI's forum and should be confirmed on Microsoft's page. Inside the first resident message never wins: a trimmed or edited history can lose the rules. | `instructions` apply to the current call only. In a test, a rule sent on turn 1 was gone on turn 2 when `instructions` were left out. | 2.3.a | "Can a resident change the assistant's rules by typing?" |
| S02 | The page must show a ticket card (category, urgency, unit, summary) that other parts of the product can read. | A second call after every reply, with a `json_schema` and strict checking, so the card always has exactly four fields and only the allowed labels | One call when the resident presses a "Create ticket" button; the card requested inside the reply itself with `json_object` | The button wins when cost matters more than a live card: the card call added 256 and 399 input tokens on turns that used 443 and 564 (58% and 71% more, one test run). `json_object` only promises valid JSON, not the fields, and would put raw data into the resident's chat. | `json_schema` guarantees the fields; `json_object` only guarantees valid JSON. The card call has its own instruction, so it can disagree with the chat's rules (an emergency rule it does not know). | 4.1.a | "How do the ticket system and the reports know what the assistant decided?" |
