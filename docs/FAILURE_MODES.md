# Failure modes

Every failure here was caused on purpose (a deliberate break) or met during the build, then diagnosed and fixed. One row per session at least.

| Session | What was changed or went wrong | Symptom (exact error) | Layer | Cause | Fix or guard | Exam skill |
|---|---|---|---|---|---|---|
| S00 | Met during the build (9 Oct): the `model` argument of the first Responses API call did not match a deployment in the project. The API takes your deployment name, not the model's name. | `openai.NotFoundError`, HTTP 404, code `DeploymentNotFound` | Intelligence (model deployment) | A deployment name is chosen in the portal and is not the same thing as the model it serves, so a name that is not an exact match finds nothing. | Copy the exact name from the project's Deployments page into `CHAT_DEPLOYMENT` in `.env`. Guard: keep the name in one setting, never typed inside the code. | 2.1.a, 1.2.c |
| S00 | Deliberate break (12 Oct): added the letter X to the project name in `FOUNDRY_PROJECT_ENDPOINT`, then restored it from a backup. | `openai.NotFoundError: Error code: 404 - {'code': 'ResourceNotFound', 'message': 'The project does not exist.'}` | Infrastructure/Operations (endpoint configuration) | The endpoint named a project that does not exist. Building the Foundry and OpenAI clients makes no network call, so the error only appears at the first `responses.create`. A 404 rather than a 401 or 403 suggests the sign-in itself worked. | Fix: restore the exact endpoint from the project overview page in the Foundry portal. Guard (not built yet): make `scripts/check_setup.py` call the project once and name the setting that is wrong. | 2.1.f |
| S01 | Met during the build (14 Oct): in portal evaluation run 1, the text for generating test data was pasted into both the System prompt and User prompt boxes. | Relevance 35% (7 of 20) and OutputQuality 51%; the model under test replied with lists of resident messages instead of answering them. | Evaluation/Reliability (evaluation set-up) | An evaluation scores the model plus its instructions plus its input template. With the wrong text in the prompt boxes the model answered the wrong task, so the low score said nothing about the model. | Fix: put the Contoso service desk instructions in the Developer box and the resident message (`{{item.query}}`) as the user prompt; run 2 scored relevance 100%. Guard: open the exported rows before judging a model. | 2.1.d, 1.4.b |
| S01 | Met during the build (14 Oct): in the first full judge run from code, 5 of 20 rows (T06, T10, T13, T17, T19) came back with no score. | Empty scores in the results file with no error text; the average covered 15 rows only. The failure rule did not warn, because it only checks failed replies. | Evaluation/Reliability (judge call) | The judge call failed for those rows and the error was discarded. Timeouts are suspected (many that evening) but the cause was not recorded. A missing score is an unknown, not a zero. | Fix: re-judged only those rows from the saved replies on 15 Oct; all 20 scored. The runner now saves the error text next to an empty score (`judge_error`); not yet exercised because no row failed. Guard not built yet: warn when fewer than 80% of rows are scored. | 2.1.d |
